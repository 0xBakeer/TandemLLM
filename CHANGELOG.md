Releases of TandemLLM. ## 0.3.21-test, 2026-10-03

A hotfix on 50cc1f5 (0.3.20-test, branch tandem-img1): a long conversation is no longer refused for the images it has gathered, and after a compaction the session's class packages come back. No serve.env key, no ops/ file, no engine file and no conductor document changes; a request whose images fit the caps and that is not a compaction or the first user message after one is served byte for byte as by 0.3.20-test.

- The bug (Khaled's opencode session in ~/rrr6, 2026-10-03): the `design-review` package (packages v6) has the model screenshot every section and read each png, and opencode sends every earlier image again on every turn. The 17th (several were re-reads of one file) took the request over `--max-images` (16): HTTP 400 `17 images; the limit is 16 a request` on `messages[210].content[1].image_url`, not retryable, and every later request carried 17 or more, so the session could never continue.
- `server/images.py`: when a request's images are over `--max-images` or `--max-image-rows` and the excess is in earlier messages, the oldest images are left out instead of a 400. A left-out image is never fetched or decoded; `build_prompt` renders it as the text `[an earlier image was left out: TandemLLM keeps the newest 16 images of a conversation]` (`images.LEFT_OUT`, one text for every left-out image of a server) in place of its placeholder, so the template writes no placeholder for it and the placeholders left match the images kept. The router, the session monitor, the outcomes and the transcripts read the client's messages unchanged; only the prompt changes.
- For the caches: images go in steps of half the cap (8 at the default), counted from the conversation's start (`images.left_out`): at 17 images the oldest 8 go and the next 7 images change nothing before the prompt, so the head the resident prefix, the state store and the disk tier resume stays the same for several turns (leaving out one image a turn would change the prompt near its start on every turn and miss every cache). Over the row cap the newest message's images are read first, then the earlier ones newest first; the first that would go over and everything older are left out, rounded up to a whole step, so a full queue still holds at most the row cap of patches. The choice is a function of the message list (and the rows of the images it keeps), so the same history always renders the same prompt.
- Only the newest message's own images are never left out: over a cap on their own, the request is the 400 it was, now `17 images in the newest message; the limit is 16 a request`, naming the first image over. The refusals of a single message (a broken image, the row cap, the encode budget) are unchanged.
- Each request that leaves images out says so: a log line `[images] <request id>: left out the oldest N of M images (the caps: ...)` with counts only, the response header `X-Tandem-Images-Left-Out: N`, `extra.images_left_out` in the journal's router row, and the counter `qse_images_left_out_total` (server/METRICS.md).
- The package side, live before this build (packages v7, 2026-10-03 14:24): `design-review` looks at at most 2 to 3 images a round (one full-page screenshot per width, or a contact sheet stitched from saved shots), never reads an image twice, about 12 in a session, and takes what needs no eyes (overlaps, overflow, contrast, fonts, empty cards) from its DOM audit text; its `max_tokens` 1600 -> 1800 for the longer text (1,692 tokens on the engine's tokenizer).
- After a compaction the class packages come back (the same session, 14:42 to 14:50): every turn before `/compact` carried the design packages (`conductor_hidden_tokens` 6,502); every turn after it carried none, and the model went looking for the Laya endpoint and the design skills on disk. The router's journal said why: opencode 1.18.34 sends its compaction request with its `compaction` agent's prompt as a system message, which the compaction shape (no system text) ruled out, so the request was routed as `design_ui` (seven packages, high effort, 2,116 reasoning tokens) and the session never knew it had been compacted; the `continue` after it was then a new user message, classified `chat` at 0.998, and chat has no package. The replay was not the cause: a note the history no longer carries is not replayed and the class's block goes in again (tests/test_conductor_router.py had that case). `server/conductor/signals.py` `COMPACTION_SHAPES` / `compaction_shape`: no tools, a system message opening with the agent's fixed instruction, the history as the one user message after it, is the compaction (class `summarize`, structural, thinking off, no package; the monitor's S2 watch reads the same flag). `server/conductor/router.py`: the first user message after a compaction keeps the session's class (`source: sticky`, `kept: after_compaction`), no classifier asked; the block goes in again at the compacted history's insertion point, the next turns replay it, and the next message a person writes is classified as any other.
- Tests (CPU): `tests/test_compaction_turns.py` (4: opencode 1.18.34's compaction request is `summarize`, thinking off, no note, no classifier; after it `continue` keeps `design_ui`, the block goes in again (tokens > 0), the tool turn after replays it, the next new message is classified; the same `continue` without a compaction is classified `chat`; the shape is exact: tools, a third message, another system text or a flipped order are not a compaction, the old shape still is); the first two fail on 50cc1f5 exactly as live (`opencode 1.18.34's compaction request`, `('chat', 'qwen')`).

## 0.2.0-staircut, 2026-09-29

Tagged `v0.2.0-staircut`: StairCut, from branch router-eng169, merged at `c111fa7`. The figures below are the release gate's same-hour runs. The paper's measurements of this release, on the published NVFP4 set, are in the [README](README.md#paper), and its classification of the 30-prompt agreement check is the one in [docs/exactness.md](docs/exactness.md).

- StairCut: `QWEN38_LEN_SWITCH=1 QWEN38_LEN_MODE=wide` cuts every round's tree (the wide drafter's lattice, its chain, the lookup tree, their merge) to the node count with the most expected tokens per millisecond on the measured verify staircase, priced by context class (`QWEN38_STAIR_TABLES`). The lookup's continuation rate on 8-token matches is a held-out prior counted online (`QWEN38_STAIR_RHO`), and `QWEN38_STAIR_SKIP=1` skips the head draft on a copy run. All flags are off in the code; `ops/serve.env` turns them on. With them off, every text is byte-identical to rc10. [docs/speculative-decoding.md](docs/speculative-decoding.md) has the rule.
- On the published NVFP4 set, the benchmark row reads 49.33 and 50.47 tok/s with the store off (50.37 and 50.60 with a clean store). Fixed block 8 reads 47.44 and 46.82 (47.71 and 46.80), and fixed block 16 reads 44.65 and 44.95 (43.80 and 44.05), all in the same hour.
- Not every text is identical. Of 30 prompts checked against plain greedy decoding, 17 are identical up to the end of the answer: 13 over all 256 tokens, and 4 more that differ only past the end of the answer. The other 13 take the other token at a near tie inside the answer, with a gap of 0.04 to 0.76 ulp, and continue from there. None differs otherwise. [docs/exactness.md](docs/exactness.md) states the rule.
- The router learns online: draft cost per context class, calibration, copy counts. A server keeps what one request teaches for the next. On the teacher-forced bench (25 workloads), a router rebuilt for every request averages 1.4 % below one that is kept.
- New tools: `tools/router_replay.py` replays router policies on recorded lattices, and `tools/forced_bench.py` measures configurations on one reference text.
