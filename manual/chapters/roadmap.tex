\chapter{Roadmap}\label{ch:roadmap}

Today the engine serves one main model (Qwen3.8-27B) with small models beside it, it is measured on one board (the DGX Spark, Section~\ref{sec:test-env}), and it decodes up to four requests at once. Each step below widens one of those limits, and each keeps the two rules that hold today: the output stays the model's greedy text, up to the documented near-tie exception, and no measured number gets worse. The steps are listed in the order they are planned. Nothing here is a promise of dates, and nothing here is measured unless it says so.

\section{A mixture-of-experts model}

The first new model is Qwen3.8-Flash-Next, a mixture-of-experts hybrid of the same family, in its published NVFP4 form. It needs expert routing inside the verify: a tree of 16 nodes can route each node to different experts, so a verify reads the union of the experts its nodes chose, its cost depends on the text, and the router has to price that. It needs the experts as W4A16 NVFP4, the rest of the weights in MXFP8, and a large per-layer embedding table kept memory-mapped rather than resident. Its built-in prediction head would be the first drafter.

By the byte math it fits: about 71.3~GiB resident without the embedding table, which stays on disk, and a bandwidth floor of about 38 tok/s at 273~GB/s (\arith, from the checkpoint headers). It never shares the board with the 27B engine, because the two together do not fit. After it, Qwen3.6-35B-A3B in its standard NVFP4 export, to check that the stack works on a checkpoint the authors did not quantise.

\section{Parallel requests}

Phase A ships, off in the shipped profile (Section~\ref{sec:parallel-requests}): side slots, the GPU turn, a packed draft and a joint verify of at most 32 rows, admission by bytes. Two requests at once reach about 1.4$\times$ the total of one, not 2$\times$: a joint pass of 32 rows costs more than one of 16 at today's kernels. Next: one engine thread for all slots, joint verify graphs and one graph pool, so a side slot costs under 3~GiB instead of 7. Later, multi-user serving with caches isolated per user, so no user can resume from another user's prefix; the proxy already gives each user a key of their own.

\section{The NVMe tier}

The disk tier shipped in 0.4.0, and its restore was measured on the board: a 10,701-token head read back in 226~ms, and after a restart the first process's files restored bit for bit to the second process's cold prefill (\measured). What remains is a background backfill of the resident prompt's chunks while the engine is idle.

\section{Profiles as data}

Today a serving profile is a \code{serve.env} file. The plan is a small profile format that a validator checks: every weight file with its format and hash, all the settings, and a facts block with what was measured (memory and disk, speed at prompt lengths from 256 to 64k tokens, quality against the reference), each number labelled with how it was obtained. The repository would ship a signed catalogue of tested profiles, and the dashboard a view to install them and switch between them, doing the byte math first, allowing one engine at a time, and rolling back if the new profile does not come up healthy.

\section{Other GPUs, then several}

Other single GPUs first (H100, H200, RTX Pro 6000, L40S). Most have no FP4 tensor cores, so they need to decode the 4-bit weights in software or run an FP8 or BF16 profile. Each needs its own tile tables, and the router needs new prices: a GPU that reads memory ten times faster moves the best tree width and drafter size. Discrete GPUs also change the memory model, since admission must count the GPU's own memory and not the system's. Then several GPUs: tensor parallel inside one server, two DGX Sparks over their 200~Gb/s link, servers with 8 GPUs. A reduction across GPUs changes the order of a floating-point sum, so row invariance needs a fixed reduction order across devices.

\section{Housekeeping}

Runtime names still carry the old project name, from the \code{QWEN38_} and \code{QSE_} variable prefixes to the metric names. They change together in one release, and the old variable names keep working for one release after that. Engine settings move from import-time globals to a settings object handed to the engine, so two engines with different settings can share a process. The engine moves into an installable package, and the dashboard's package goes to PyPI.
